# DB 설계 후속 결정

## 유지할 기준

- 가계부별 독립 카테고리와 기존 UUID를 유지한다. 초기 추천값은 사용자가 수정·삭제한다. 공통 사전/가계부 설정 테이블 분리는 필요하지 않다.
- 카테고리 이름은 참조 키가 아니다. 동명 허용 정책은 소분류 구현 전에 정하며 자동 병합하지 않는다. 미분류는 이름이 아닌 시스템 식별값으로 판별한다.
- profiles/household_members는 계정과 귀속의 서로 다른 역할이다. 이름 동기화는 [이름 계획](profile-payment.md), 분류 관계는 [소분류 계획](subcategories.md), 유효 설정 이력은 [예산 계획](monthly-budget-inheritance.md)을 따른다.

## 기능 구현 시 결정

- 계정 탈퇴: 현재 auth.users → household_members는 CASCADE이나 거래 FK가 구성원 삭제를 막을 수 있다. 탈퇴 기능 전에 user_id 연결만 해제해 구성원/거래 ID를 보존하는 정책과 탈퇴 구성원 표시를 정한다. 거래 연쇄 삭제는 사용하지 않는다.
- 이름 규칙: 가계부·구성원·프로필·카테고리의 공백 처리/길이/문자 수 기준을 해당 입력 기능과 함께 DB에서 보장한다. 기존 데이터 사전 검사 후 제약을 추가한다.
- 사용자 정렬: 현재는 생성 시각과 ID로 안정적으로 정렬한다. 순서 변경 기능을 제공할 때 가계부별 sort_order를 추가하며 기본 순서도 그때 정한다.

## 측정 후 결정

- transactions의 가계부·날짜 인덱스와 실제 월 범위/유형/날짜·생성시각·ID 정렬을 EXPLAIN (ANALYZE, BUFFERS)로 확인한다. 병목이 확인되면 복합 인덱스를 검토한다.
- categories(household_id)와 (household_id,type), household_members의 단일/복합 인덱스는 선두 컬럼이 겹친다. 사용량·실행 계획 없이 제거하지 않는다.
- 월 전체 거래를 500건씩 OFFSET 조회해 앱에서 합산한다. 다중 페이지 중 동시 변경으로 중복/누락 가능성이 있으므로 데이터 증가·여러 달 통계 시 스냅샷 일관성을 가진 서버 집계/조회와 키셋 페이지를 검토한다. 현재 운영 지연이나 병목은 측정하지 않았다.
